# Проверка в matheducator

Страница описывает выбор хостом новой или старой модалки для конкретного
задания. Механизм обеспечивает поэтапную миграцию и сопоставление обоих UI на
одинаковых данных урока.

### Как увидеть правки в учебном приложении

Меняете код в `new-task-modal`. Держите сборку в фоне (`pnpm build:watch`),
чтобы папка `dist/` всегда была свежей. Хост MathEducator смотрит не в исходники
соседней папки, а именно в этот `dist/` — так настроено в webpack. Запускаете
хост на порту 8888 и жёстко обновляете страницу урока.

Отдельный пакетный менеджер вроде yalc здесь не нужен: достаточно соседних
папок и alias на `dist/`.

```bash
# терминал 1
cd new-task-modal
pnpm build:watch

# терминал 2
cd matheducator/reactjs_client
npm start
```

На хосте модалка и белый список заданий подгружаются лениво из пакета
`@qalan/new-task-modal` (см. TaskModalController в клиенте).

### Откуда берётся пакет

Есть два разных пути, и их легко перепутать.

**Локальная разработка (`npm start` / `npm run dev`).** Webpack-конфиг
дев-сервера (`webpack.config.js`) специально указывает alias на соседнюю
папку `../../new-task-modal/dist` (и на `available-tasks.js` рядом). Пока
этот alias включён, хост не ходит в то, что стоит в `node_modules`, — он
берёт вашу свежую сборку. Значение `@qalan/new-task-modal` в `package.json`
для этого пути **не важно**: достаточно `pnpm build:watch` в `new-task-modal`
и перезагрузки страницы, ничего в `reactjs_client` менять не нужно.

**Сборки (`npm run build`, `build_local`, `build_test`) и обычный `npm install`
без alias.** Эти webpack-конфиги (`webpack.production.config.js`,
`webpack.local.config.js`, `webpack.test.config.js`) alias не объявляют — они
резолвят `@qalan/new-task-modal` как обычную зависимость из `node_modules`. В
`matheducator/reactjs_client/package.json` эта зависимость сейчас —

```json
"@qalan/new-task-modal": "github:amirali-kadenov/new-task-modal#2.0.3"
```

Если нужно проверить локальные правки `new-task-modal` именно через один из
этих build-скриптов (не через дев-сервер) — временно верните
`"file:../../new-task-modal"` в этой строке, переустановите зависимости,
после проверки верните git-тег обратно перед коммитом.

Установка с тега на GitHub — **временное** решение. Дальше нужно настроить
доступы и публиковать / подтягивать пакет из **внутреннего** репозитория
пакетов (корпоративный registry), а не с публичного GitHub.

#### Почему тег ссылается на отдельный «prebuilt» коммит, а не просто на `main`

`reactjs_client` на некоторых машинах (в т.ч. проде) работает на **node 13.7**
— этот пакет свою сборку (Vite/esbuild/tsx…) на node 13 не запустит, там
нужен node ≥18–20+. Обычный git-тег с исходниками заставил бы
`npm install`/`prepare` собирать пакет прямо во время установки — упадёт.

Поэтому теги `2.0.1+` указывают не на коммит из `main`, а на отдельный
"release"-коммит: там уже лежит собранный `dist/` (закоммичен через
`git add -f`, обычно он в `.gitignore`), а `prepare`/`postinstall` из
`package.json` убраны — устанавливать/собирать во время `npm install`
нечего, тег просто клонируется как есть. `main` при этом остаётся
source-only (`dist/` игнорируется, скрипты сборки на месте) — так задумано,
release-ветки в `main` не мержатся.

#### `npm install` под node 13 — рабочий, но очень медленный. Используйте yarn

`package-lock.json` в `reactjs_client` сгенерирован современным npm
(`lockfileVersion: 3`), а на node 13 стоит **npm 6**, который этот формат не
понимает нативно и на каждой установке перезапрашивает метаданные пакетов по
одному (нет bulk-эндпоинта в том протоколе) — это реально **10–20 минут** на
пустом месте, не зависание.

`yarn.lock` уже в репозитории и это его нативный формат — конфликта версий
лока нет. Ставьте зависимости через **Yarn Classic** (не через corepack —
его собственный shim на `??=` не парсится на node 13, упадёт с
`SyntaxError`; нужен отдельный бинарник, например `brew install yarn`):

```bash
yarn install --ignore-engines
```

`--ignore-engines` обязателен: yarn (в отличие от npm, который на
`engines`-несовпадение только предупреждает) по умолчанию **падает** на
первом же транзитивном пакете с `engines.node` выше 13 — в этом дереве такой
пакет есть у `@grafana/faro-*` (не связано с new-task-modal).

На той же машине (node 13.7, npm 6, git-тег `2.0.3`) `npm install` занял
**~17 минут**, `yarn install --ignore-engines` — **39 секунд**.

### Зачем белый список заданий

Не каждое задание сразу идёт в новый UI. Хост открывает новую модалку только
для ключей из списка `availableTasks`. Список собирается из глав классов и
явных соответствий, командой `pnpm generate-available-tasks`. После смены глав
пересоберите список и убедитесь, что в `dist/` обновился файл белого списка.

### Если на хосте «ничего не меняется»

Сначала проверьте, что `dist/` свежий (идут ли пересборки от `build:watch`).
Потом — что webpack действительно указывает на соседний `new-task-modal/dist`.
Потом — что ключ задания есть в главах / карте и попал в белый список. В конце —
жёсткое обновление страницы в браузере.

Задание вне списка всегда откроет старую модалку, даже если шаблон уже написан.
Параметр `?old` в адресе тоже принудительно включает старый UI — так сравнивают
два варианта на одних данных.

Статус «шаблон есть в коде / в манифесте / в белом списке» удобно смотреть в
**Statistic → Главная → Покрытие**. В деплое Storybook на тест/прод это
offline-снимок с момента `build-storybook:test` / `:prod` (флаг
`VITE_STATS_STATIC`), не live-сервер.

Как хост лениво подгружает пакет и стили — в
[Internals](?path=/docs/internals-обзор--documentation).
